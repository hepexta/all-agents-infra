# The database is a single primary managed by the chart, not by an operator

The platform needs a production-shaped PostgreSQL that can be installed into the local cluster and into the managed service with the same chart, and the obvious alternative was an operator that owns replication, failover and point-in-time recovery. We chose a plain single-primary workload with scheduled dumps instead: the database is small, its availability requirement is a research platform rather than a customer-facing service, and an operator would add a cluster-scoped component with its own custom resources, its own upgrade path and its own failure modes to a repository whose whole point is testing ordinary chart mechanics. The cost is stated rather than hidden. There is no automatic failover: if the pod or its node is lost, the database is unavailable until it reschedules, and a second replica would not be promoted on its own. There is no point-in-time recovery: the safety net is the scheduled dump, so the worst case is the time since the last dump. The restore-on-start behaviour of the container stack was deliberately not carried over, because in a cluster it would let a readiness probe report the database as available while it was still overwriting writes. If availability requirements change, the operator route is the recorded alternative rather than a rewrite of this decision.
